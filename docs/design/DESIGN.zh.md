# paper-craft 设计决策

[English](DESIGN.md)

paper-craft 的技术架构决策。这些选择承载着整个系统——改变它们会产生广泛影响。

## 模块化设计

模块遵循以下原则：

- **正交与低耦合（Orthogonality & Low Coupling）**：尽可能减少模块之间的相互依赖，保持各模块职责独立与正交；避免即使在小接口下仍形成网状纠缠，将单点修改的影响严格限制在模块内部。
- **深模块与高杠杆率（Deep Module & Leverage）**：对外暴露极小的接口表面积（接缝 Seam），在内部封装复杂的实现逻辑与状态；为调用方提供高杠杆率（Leverage），为维护方提供高局部性（Locality），杜绝无实效的浅层透传（Pass-through）。

## 技能与执行的边界

已商定的目标架构将专业任务知识与流程策略分离。本节描述重构目标，而非当前实现。

- **技能**：教导如何完成一项完整的专业任务。专业技能不知道 workflow 或 orchestrator 的存在，不要求安装 paper-craft CLI。允许真正需要的其他技能依赖；不包含派发专用模式或回执命令。
- **任务契约**：声明一种任务的输入、输出和验证要求，不依赖其流程位置或执行者。契约放在执行模块中，位于专业技能目录之外。初期只为默认 orchestrator 流程使用的任务提供契约。
- **执行辅助**：解析契约输入、组装 prompt、启动 agent、验证并记录结果，以及管理执行身份和资源。不选择后续任务，也不解释流程跳转图。
- **Orchestrator**：负责步骤顺序、执行者选择、结果关联、失败分支和整体完成判断。它理解失败原因以选择后续工作，但不手动复制发现或组装输入字段。脚本将选定的前序结果解析为下一项任务的输入。

每次派发都开启新的 agent 对话，包括重复角色和修复尝试。上下文通过明确输入传递，不复用对话。执行状态与业务结论分离：正常完成的审查可以得出需要修改的结论。脚本验证契约，专业 agent 提供领域判断。

将 orchestrator 的计划与执行记录分别持久化。计划记录目标、步骤、执行者与调整；执行记录保存任务身份、输入关联、状态、结果与资源。恢复时读取两者。脚本不自动推进计划。保持模块接口精简、职责正交。

## 默认编排参考

默认顺序放在 orchestrator 技能中，作为可修改的参考，而非可执行的跳转规则。用户可以通过指令改变顺序。本设计记录预期默认流程，具体操作规程由技能负责。

1. 调用 `pc-issue-plan`，判断是否需要子 issue 并形成计划。
2. 按依赖顺序处理各 issue：调用 `pc-issue-work` 实现并验证，再调用 `pc-pr-land` 创建或更新 PR、调用 `pc-pr-review`，通过验证后合并。发现的问题返回 orchestrator，由其重新派发修复任务。
3. 调用 `pc-issue-plan`，根据合并后的交付证据核验原始目标。它报告缺口，不自行调度修复。
4. 调用 `pc-pipeline-refactor`，只整理本次工作涉及的流水线文件。保持科学方法、结果和结论不变；同步受影响的路径引用，进行必要的结构与可运行性检查，不重跑无关计算。需要改变计算逻辑的修改应报告为超出范围。
5. 如果文件整理产生变更，派发新的 `pc-pr-land` agent 交付。仅因文件整理，不额外安排科学目标验收。
6. 调用 `pc-research-state`，记录最终研究状态、产物位置和复现入口。

`pc-pr-land` 负责交付到目标分支，不负责释放工作目录。执行辅助负责资源生命周期。检查全部专业技能中的流程认知和混杂职责；保留有用的专业协作，不为每个操作新增一个技能。
