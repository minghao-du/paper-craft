# /pc-skeptic

Audit surprising, strong, or negative computational research results before follow-up work or theoretical explanations are built upon them. Find the simplest explanation for an unexpected finding.

## Core Audit Checklist

State each claim precisely. Record the expected result and its basis in a mathematical bound, comparable benchmark, or prior run. Identify any uncertainty about whether the expectation applies.

Work through the checks in order. Close a claim early when evidence establishes that the evaluation cannot support it, as when test-label leakage invalidates an estimate of generalization to unseen samples. For a suspected numerical bias, use a corrected comparison or justified bound to assess its impact. If a correction changes the magnitude but leaves a difference, record both and continue auditing any claim about the remaining difference.

### 1. Software Bugs & Mechanical Failures
- **Reproduce on a trivial synthetic case**: Construct an extreme case where the ground truth is mathematically certain. If the case fails, verify the fixture and trace the discrepancy to the path used for the reported result.
- **Input integrity**: Verify file paths, array orientations, 0- vs 1-based indexing, coordinate offsets, and unit conversions.
- **Git blame on critical paths**: Check if the surprising behavior coincides with a recent refactor or optimization.
- **Silent error swallowing**: Inspect stderr, try/catch blocks, and return codes for ignored warnings or non-converged optimizations.

### 2. Asymmetric Evaluation & Information Leaks
- **Scoring asymmetry**: Does the evaluation metric favor one method? (e.g., evaluating alignments using ancestor reconstructions generated by the same algorithm under test).
- **Condition equivalence**: Identify which conditions the claim holds fixed and verify them across methods. For an equal-compute claim, compare actual compute cost. For a tuned-performance claim, compare tuning budgets, validation data and selection rules while allowing method-specific hyperparameters.
- **Information leakage**: Does any condition inadvertently receive ground truth, test labels, or oracle statistics?

### 3. Plausibility of Effect Size
- For rates and percentage differences, inspect counts, denominators, sample size and variability. Check whether the task or a mathematical constraint predicts an extreme rate.
- For aggregate scores such as total log likelihood, verify units and normalization and compute the difference per observation. Check that datasets, scoring rules and evaluation conditions support comparison with the reference.
- When a negative result is used to rule out a meaningful effect, identify the effect size the claim excludes. Check whether the evidence supports that limit, using a justified uncertainty interval or the pipeline's recovery rate for signals of that size injected into representative data. Report which effect sizes remain compatible with the result.

### 4. Root Assumption Tracing
- Map the dependency graph of assumptions leading to the result:
  `Claim -> Metric -> Loader -> Data preprocessing -> Upstream artifact`.
- Check if upstream intermediate artifacts were independently verified or if a flaw in an earlier step propagated downstream.
- When a claim generalizes beyond the reported metric, state what the metric measures, which population it represents, and how observations are weighted. If another scientifically justified definition or weighting could change the conclusion, recompute the comparison on the same records under that choice. Scope each conclusion to the population and measurement it supports.

### 5. Occam's Razor
Use simple explanations to prioritize checks. Base the verdict on evidence of their impact:
- A buggy scoring metric is simpler than "the algorithm class is fundamentally broken".
- Unfair parameter tuning is simpler than "established theory fails here".

## Verdict Format

Report separately for each claim:
- **Claim**: Exact statement of the surprising result.
- **Surprise Level**: Routine / Notable / Extraordinary, with the expected result and its source. Mark the level undetermined if the expectation lacks support.
- **Identified Concerns**: Ordered list of concrete discrepancies, bugs, or asymmetries found in code or configuration.
- **Validation Test**: Give the command or check and its observed outcome. Mark pending checks explicitly and state which inference depends on them.
- **Verdict**:
  - `[CREDIBLE]`: The checks support the stated claim within the audited conditions.
  - `[CHECK FIRST]`: A material concern remains unresolved. Name the evidence needed to settle it.
  - `[SUSPECT]`: A confirmed flaw invalidates the evidence for this claim. State which inference fails.
